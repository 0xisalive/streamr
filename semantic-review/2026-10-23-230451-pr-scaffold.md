# Streaming pipeline scaffold: embedded torrent engine, transcode decision, tiered subtitles

This branch lands the entire Go backend for streamr: a source resolver that fans out to Torznab/Newznab indexers, two torrent engines (embedded anacrolix + a qBittorrent WebUI driver), an ffprobe-driven direct/remux/transcode decision, an HLS transcode delivery path, a tiered subtitle alignment pipeline with a Whisper-generation fallback, a SQLite cache, and the HTTP/JSON API that wires it all behind a React SPA. The design is coherent and the concurrency model is thought through — per-session serialization on the shared reader, a parallel resolver fan-out, background subtitle jobs, and an idle-session sweeper. Build, `go vet`, and the unit suite all pass.

The problem is that several of the headline delivery paths don't actually reach the browser in a playable state. The HLS playlist URL is handed to the client before ffmpeg has written the playlist, so transcode delivery 404s on first load. The subtitle `<track>` is wired with a URL that 404s until the async job finishes, with no retry, so subtitles never appear for the common case. And because the default (embedded) engine's reader reports no on-disk path, probing is skipped and *every* stream is classified DirectPlay — meaning the remux and transcode paths are effectively dead for the default configuration, and HEVC/mkv content silently won't play. There is also a genuine use-after-free window where the idle sweeper can drop a torrent / close a reader while a stream handler is mid-read.

Watch for:
- **HLS playlist served before it exists** (confirmed) — transcode delivery 404s until ffmpeg writes `index.m3u8`; no readiness wait.
- **Subtitle track never loads** (confirmed) — `<track>` points at `/api/subtitle/{id}` which 404s until the background job finishes; the browser fetches once and gives up.
- **Default engine never remuxes/transcodes** (confirmed) — anacrolix reader's `Name()==""` skips probing, so Decide never runs and every stream is DirectPlay; HEVC/AC3/mkv won't play in-browser.
- **Idle GC use-after-free** (confirmed) — `remove()` calls `stream.Close()` (torrent Drop / file close) without holding `serveMu`, racing an in-flight `ServeContent`.

**Verdict**: NEEDS_CHANGES

## High-level view

The streaming correctness hinges on `videoPathOf(stream)`. For the qBittorrent engine it returns an `*os.File` path and the whole probe→Decide→remux/transcode chain works. For the *default* embedded engine it returns `""` by design, which short-circuits probing, subtitle audio extraction, and delivery-mode selection — so the default install only ever does DirectPlay and quietly fails on the mkv/HEVC content that the README says is the common case. This is the single most consequential behavioral gap in the branch.

HLS transcode delivery has a readiness race: `startHLS` launches ffmpeg and immediately returns the `index.m3u8` URL, but ffmpeg writes the playlist asynchronously, so the client's first fetch 404s. The comment in `StartHLS` even says "the caller polls for the playlist to appear" — but no caller does. hls.js will retry some, but the initial load is broken and there's no guaranteed recovery.

Subtitles are produced on a background goroutine and exposed at `/api/subtitle/{id}`, but the frontend renders the `<track>` immediately with that URL. The browser fetches it once, gets a 404, and never retries — so in the normal case (sub not ready at play time) subtitles silently never appear. The backend has no readiness signal the client can poll.

Session lifecycle has a real race rather than just a leak: the idle sweeper's `remove()` tears down the stream (torrent Drop, reader Close) without coordinating with the `serveMu` that guards active reads, so a sweep can free the reader out from under an in-flight `ServeContent`. Separately, the per-session `serveMu` serializes *all* concurrent Range requests for one session across the entire response duration, which stalls the second connection (hls.js and some players open several) for the length of the first.

The subtitle "never ship a worse subtitle" gate is mostly sound, but has two holes: ffsubsync returns a hard-coded 0.6 confidence when it can't parse a score, which can push a silently-stretched sub past the default 0.55 gate; and the Whisper-generated fallback is assigned a fixed 0.85 confidence and cached as authoritative regardless of actual transcription quality.

The HLS file handler's path-traversal guard (`filepath.Base`) is correct. The SPA handler's `filepath.Clean` on the request path is *not* a traversal guard on its own and should be reviewed. CORS is wide-open `*` with no credentials, which is acceptable for a LAN tool but worth a conscious decision.

<summary>Issues (12)</summary>

1. **HLS playlist served before it exists** — `startHLS` returns the `index.m3u8` URL without waiting for ffmpeg to write it; add a bounded poll for the playlist (and first segment) before returning the URL, or have `handleHLS` hold/long-poll until the file appears.
2. **Subtitle track 404s and never loads** — frontend sets `<track src>` to an endpoint that 404s until the async job finishes; add a readiness/poll mechanism (e.g. `/api/subtitle/{id}` returns 202 until ready, client polls then injects the track) instead of rendering it up front.
3. **Default engine never leaves DirectPlay** — anacrolix reader `Name()==""` disables probing, so HEVC/AC3/mkv is mislabeled DirectPlay and won't play; stage the partial file to a real path (or expose the anacrolix file path) so Probe/Decide can run.
4. **Idle-GC use-after-free on the reader** — `sessionManager.remove()` calls `stream.Close()` without holding `serveMu`; coordinate teardown with the serve lock (or a per-session refcount/cancel) so a sweep can't free the reader mid-`ServeContent`.
5. **serveMu serializes distinct connections for the whole response** — the per-session lock is held for the full `ServeContent` duration, blocking a second concurrent Range request for the length of the first; consider a seekable per-request reader or a short seek-only lock.
6. **ffsubsync parse-miss confidence can beat the gate** — a failed score parse returns 0.6, above the 0.55 default `minConfidence`, so a silently-stretched subtitle can be accepted; treat a parse miss as low/zero confidence or verify independently.
7. **Whisper-gen confidence is fabricated** — generation is hard-coded to 0.85 and cached as authoritative; it bypasses the "never worse" gate and poisons the cache with potentially bad timings. Derive confidence or mark generated subs as non-authoritative.
8. **Transcode mode falls through to ServeContent** — if `startHLS` fails it falls back to DirectPlay, but a session left in `Transcode` mode with no HLS dir reaching `handleStream` serves the raw (unplayable) bytes; make the fallback explicit and guard `handleStream` against Transcode mode.
9. **Remux stream has no cancel on GC / reader contention** — `RemuxToWriter` runs ffmpeg bound to the request context but reads `sess.videoPath` concurrently with other readers of the same partial file; confirm the partial file supports concurrent readers and that GC can't delete it mid-remux.
10. **SPA handler traversal guard is thin** — `filepath.Clean(r.URL.Path)` joined to webDir is not by itself a traversal guard; verify `..` can't escape `webDir` (the stdlib FileServer protects itself, but the `os.Stat`/`ServeFile(index.html)` branch is hand-rolled).
11. **HLS/subtitle temp dirs not cleaned on teardown** — `remove()` stops ffmpeg and drops the torrent but never removes `data/hls/{id}` or `data/subs/{id}`; disk grows unbounded across sessions. Remove the session dirs on teardown.
12. **CORS is `*` for all origins** — fine for a single-user LAN deployment but an explicit decision; if the API is ever exposed, lock it down.

<summary>Details</summary>

### videoPathOf gates everything — and the default engine returns ""

`startPlayback` only probes, picks a delivery mode, and extracts subtitle audio when `videoPathOf(stream) != ""` (server.go:233-245, 290-296). `videoPathOf` reaches into the reader for a `Name() string` method (server.go:461-470). The qBittorrent engine backs the reader with an `*os.File`, whose `Name()` is the real path — good. The embedded anacrolix engine deliberately returns `""` (anacrolix.go:140-146, and the doc comment is explicit about it).

The consequence is not graceful degradation, it's a silent capability loss for the *default* configuration (`Engine: "embedded"`, config.go:52). With no path:

- probing is skipped, so `Decide` never runs and `mode` stays `DirectPlay` (server.go:235);
- HEVC/AC3/DTS/mkv — which the README calls the common torrent case — are served as raw bytes and won't play in-browser;
- the subtitle job early-returns before doing anything (server.go:290-293), so the embedded engine produces no subtitles at all.

So the two marquee features (transcode-anything, always-on subtitles) are inert on the engine the project ships by default. ffprobe *can* read a partial file by path, and anacrolix writes pieces to `dataDir`; the fix is to expose or stage that on-disk path rather than returning `""`. Until then the honest status is "direct-play only" for the default build, which should at minimum be surfaced loudly rather than presented as working.

### HLS playlist handed out before ffmpeg writes it

`startHLS` starts the transcode and immediately returns `/api/hls/{id}/index.m3u8` (server.go:259-271). `Transcoder.StartHLS` launches ffmpeg with `cmd.Start()` and returns without waiting (transcoder.go). ffmpeg writes `index.m3u8` only after it has muxed the first segment, which for a re-encode is seconds away. In between, `handleHLS` → `http.ServeFile` returns 404 (server.go:360-375).

`StartHLS`'s own doc comment says "The caller polls for the playlist to appear before serving it" — but `startHLS` doesn't, and nothing else does either. hls.js retries manifest loads a bounded number of times, so this *may* self-heal, but it's a race the code claims to handle and doesn't. The fix is a bounded wait (poll for `index.m3u8` + at least one `.ts`, or have `handleHLS` long-poll/`202` until the file exists) before the client is told to load it.

### Subtitle track points at a 404 and never retries

The play response always includes `"subtitle_url": "/api/subtitle/" + id` (server.go:249), and the subtitle is produced on a 30-minute background goroutine (server.go:299-330). `handleSubtitle` returns 404 while `sess.subtitle == ""` (server.go:391-399). The frontend renders `<track src={subtitle_url} default>` as soon as it has the URL (Watch.tsx), so the browser fetches the track exactly once at load, gets 404, and never tries again.

Net effect: for anything not already cached, subtitles never show up, even after the job completes. There's no readiness channel the client can poll — the progress endpoint reports download fraction, not subtitle status. Either return `202` from `/api/subtitle/{id}` while pending and have the client poll then inject the `<track>` once it's `200`, or add a subtitle-status field to the progress response.

### Idle sweeper can free the reader mid-read

The stream handler serializes reads on `sess.serveMu` and holds it for the entire `ServeContent` call (server.go:352-354) — which for a movie is the whole playback. The idle sweeper's `remove()` calls `s.stream.Close()` — anacrolix `t.Drop()` / `reader.Close()`, or the qBittorrent file close + torrent delete (session.go:88-95) — **without** acquiring `serveMu`.

`get()` touches `lastAccess` on every request (session.go:69-76), so an actively-playing session won't normally be swept. But a paused player past the idle timeout is exactly the case the GC targets, and a resumed/seeking Range read can be in `ServeContent` at the moment the sweep fires, since the browser may hold a connection open. Dropping the torrent and closing the reader underneath an in-flight read is a use-after-free on the reader (anacrolix) or a read on a closed `*os.File` (qBittorrent) — at best an error to the client, at worst a panic deep in the torrent library. Teardown needs to coordinate with the serve lock (acquire `serveMu` before Close, or use a cancelable context + refcount so Close waits for readers to drain).

### serveMu serializes connections that should be independent

The lock comment acknowledges the design ("the lock only matters when a client opens several connections to one session," server.go:347-351). That case is not rare: hls.js, and the `<video>` element itself under some browsers, open multiple concurrent Range connections. Because the lock wraps the whole `ServeContent`, the second connection blocks for the entire duration of the first response rather than just long enough to seek — so a parallel Range request effectively hangs until the first finishes streaming. A single shared `ReadSeeker` genuinely can't serve concurrent seek+read, but the fix is to give each request its own reader (anacrolix `File.NewReader()` is cheap and per-reader prioritized) rather than globally serializing. As written, concurrent range serving — which the test `TestConcurrentStreamRequests` claims to exercise — only passes because every goroutine requests the same small range and the memReader returns instantly; it doesn't exercise the stall.

### Confidence gate: two ways a worse/unknown sub ships

The pipeline's "never worse" guarantee (pipeline.go:72-115) is the right design — run tiers cheap-first, keep the original unless a tier clears `minConfidence`. Two inputs to the gate undermine it:

ffsubsync returns a hard-coded `0.6` when it can't parse a score from stderr (ffsubsync.go:70-74). The default `minConfidence` is `0.55` (config.go:49), so a parse miss *passes the gate* and the aligned file is accepted — precisely the silent-framerate-stretch failure mode the package comment says it guards against. A parse miss should map to a low/zero confidence (keep original), not a modest pass.

The Whisper-gen fallback is assigned a fixed `confidence = 0.85` (coordinator.go:176) and then cached via `PutVTT(..., confidence)` (coordinator.go:198) as authoritative. Generated timings are usually in sync, but model quality varies wildly by model size and audio; stamping 0.85 unconditionally and persisting it means a bad transcription is cached and reused across restarts with no path to re-derive. Generation also bypasses the gate entirely (it runs only when alignment produced nothing), which is defensible, but the fabricated confidence number shouldn't be treated as a real score.

### Transcode fallback leaves an inconsistent session

If `StartHLS` fails, `startHLS` logs and returns the direct URL (server.go:263-266) — but `sess.mode` was already set to `Transcode` by the caller before `startHLS` ran (server.go:237-239), and `hlsDir` is left empty. A subsequent `handleStream` for that session sees `mode == Transcode` (not Remux), falls past the remux branch, and serves raw bytes via `ServeContent` (server.go:333-354) — i.e. the unplayable original the transcode was meant to avoid. The fallback should reset `sess.mode = DirectPlay` so the state is consistent, and `handleStream` should explicitly reject/redirect Transcode-mode sessions rather than silently serving raw bytes.

### Temp dirs leak on teardown

ffmpeg process lifecycle is handled (HLS cancel wired into `hlsStop`, remux bound to the request context, `remove()` calls `hlsStop()` before dropping the stream, session.go:88-95). The gap is on disk: `startHLS` writes to `data/hls/{id}` and the subtitle job to `data/subs/{sessionID}`, but `remove()` never deletes either. Every session leaves its HLS segments and extracted `ref.wav` + intermediate `.srt`/`.vtt` behind, so disk grows without bound across a long-running instance — the exact "resources accumulate and leak" failure the session doc comment says this design exists to prevent. Teardown should `os.RemoveAll` the per-session HLS and subs directories.

### SPA traversal guard is hand-rolled

`handleHLS` reduces the user-supplied `{file}` to `filepath.Base(file)` before joining to `hlsDir` (server.go:366-368), which strips any `..`.

The SPA handler is hand-rolled: it `filepath.Clean(r.URL.Path)`, joins to `webDir`, `os.Stat`s, and either delegates to the stdlib `FileServer` or serves `index.html` (server.go:402-414). `filepath.Clean` on a path that starts with `/` won't by itself prevent a crafted `..` sequence from being joined outside `webDir` in the `os.Stat` branch. The stdlib `FileServer`/`ServeFile` has its own protections, but mixing a manual `os.Stat(filepath.Join(webDir, Clean(path)))` with a direct `ServeFile` warrants an explicit containment check (verify the cleaned path stays within `webDir`).

### CORS wide-open; qBittorrent login can go cleartext

`withCORS` sets `Access-Control-Allow-Origin: *` for every response with no credentials and no auth anywhere in the stack (server.go:490-502) — an explicit decision to confirm if the API is ever exposed beyond a LAN. The one credential-handling path is the qBittorrent login (qbittorrent.go:56-78), which posts user/pass over whatever scheme `qbit_url` specifies; if that's plain `http://` the WebUI password crosses the network in cleartext. Warn when `qbit_url` is non-TLS.

### Smaller behavioral notes

The remux branch sets `Accept-Ranges: none` and streams a live pipe (server.go:337-343) — correct for fragmented MP4, but seeking is dead in remux mode, so scrubbing won't work for any mkv-with-playable-codecs title.

The anacrolix `addTorrent` infohash branch swallows the error from `AddTorrentInfoHash` with `t, _ :=` (anacrolix.go:118-121); if that ever returns a nil torrent the subsequent `t.GotInfo()` panics. This path is reachable via the dedup-preferred infohash key.

`cacheKeyErr` in the store is dead code kept alive by `var _ = cacheKeyErr` (store.go); harmless, worth deleting.
